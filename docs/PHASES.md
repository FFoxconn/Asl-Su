# Build Phases

Each phase lands as its own change set and must build/run cleanly before the next one starts.

- [x] **Phase 1 — Repo & tooling scaffold**: monorepo layout, backend solution (5 src + 4 test projects, empty), Vite web app, Expo mobile app, `.gitignore`, `docker-compose.yml`.
- [x] **Phase 2 — Backend skeleton end-to-end**: `AslSuDbContext` with `User` table, first migration (`InitialAuth`), JWT login/refresh pipeline (`AuthController`), lazily-validated `JwtOptions`/connection string (fails fast at host startup, not before test/config overrides apply), Swagger with Bearer auth, Serilog console sink, dev-only auto-migrate + configurable admin seeding (`Seed:AdminEmail`/`Seed:AdminPassword`), `HealthController`; web (React Router + context-based auth) and mobile (React Navigation + Expo SecureStore) login screens + protected Dashboard shells hitting `/api/health`. Verified via 7 passing `AslSu.Api.IntegrationTests` (SQLite-backed, full request pipeline) — a real SQL Server round trip needs `docker-compose up` since this sandbox has no Docker daemon.
- [x] **Phase 3 — Core domain model**: all remaining entities added (Product, StoreProductInventory, Store, Category, Brand, Customer, Order, OrderItem, SyncLog, WebhookLog, BatchRequestLog) via the `AddCoreDomainModel` migration, with unique indexes on `Product.Sku`, `Product.Barcode`, `Store.Code`, `StoreProductInventory(ProductId, StoreId)`, `Order.PackageId`, and `WebhookLog.ExternalEventId` in place ahead of the phases that populate Order/Batch/Webhook data. `CatalogController` (stores/categories/brands), `ProductsController` (full CRUD), and `StockPriceController` (per-store stock/price upsert) are wired and JWT-protected. Web gained a Products page (add product, add store/category/brand, inline per-store stock/price editor); mobile gained a read-only Products list screen. Verified via 17 passing integration tests (10 new: product CRUD, duplicate SKU/barcode conflicts, stock/price upsert, auth-required checks).
- [x] **Phase 4 — TrendyolGo client + config + Test Connection**: `AslSu.TrendyolGo` project has `TrendyolGoOptions` (SupplierId/ApiKey/ApiSecret/BaseUrl/AgentName/ExecutorUser — BaseUrl/AgentName/ExecutorUser deliberately left unset rather than guessed, required in Production only), an auth `DelegatingHandler` (Basic Auth, `{SupplierId} - SelfIntegration` User-Agent, x-agentname/x-executor-user, TLS 1.2+), typed exceptions (`TrendyolAuthException`/`TrendyolRateLimitException`/`TrendyolApiException`) with 429/5xx retry-with-backoff, and an `ITrendyolConnectionTester` that probes the given GET packages endpoint and maps results to the exact user-facing messages specified (success / 401 / 403 / 429 / 5xx / not-configured). `TrendyolSettingsController` exposes a read-only masked view (no write endpoint — credentials are config-only) and `POST /test-connection`, logging every attempt to `SyncLogs` without ever logging secrets. Web gained an API Ayarları page with the Test Connection button. Verified via 15 new TrendyolGo unit tests (auth header construction, status-to-exception mapping, connection tester scenarios) + 4 new integration tests — 36 tests total, all passing.
- [x] **Phase 5 — Product sync (push)**: `BatchSplitter` (default max 1000 items/batch, TODO: verify against docs), `ITrendyolProductClient.CreateProductsBatchAsync`, `IProductSyncService.PushUnsyncedProductsAsync` (pushes NotSynced/Failed products in batches, updates `TgoSyncStatus`/`TgoLastSyncDate`/`TgoLastError`, writes one `BatchRequestLog` row per batch). `TrendyolSyncController`: `POST /products/push`, `GET /batch-requests`. Web Products page has a "Trendyol Go'ya Aktar" button. **Limitation**: the createProducts endpoint's exact path/payload was never given in the integration brief (unlike price-and-inventory and packages-GET) — rather than guess a URL, `TrendyolGoOptions.ProductsEndpointPath` starts empty and the client returns a clear "not configured" failure (each product ends up `Failed` with that message) until it's set from developers.tgoapps.com. All the batching/tracking/UI plumbing is real and tested (12 new TrendyolGo unit tests + 5 new integration tests, 53 tests total) — only the final outbound call is gated pending real docs.
- [x] **Phase 6 — Stock/price sync + batch polling**: `ITrendyolInventoryClient.PushPriceAndInventoryBatchAsync` calls the real given endpoint (`POST /integrator/product/grocery/suppliers/{sellerId}/products/price-and-inventory`). `IStockPriceSyncService.PushChangedInventoryAsync` finds only `StoreProductInventory` rows never synced or whose `Quantity`/`SalePrice` differ from `LastSyncedQuantity`/`LastSyncedSalePrice` (true delta-only push), batches them, and only advances the last-synced markers on success — a failed batch is retried automatically next time. `IBatchPollingService.PollPendingBatchesAsync` polls every `Pending` `BatchRequestLog` row via `ITrendyolBatchResultClient` and updates its `Status`/`SuccessCount`/`FailureCount`/`FailureReasonsJson`; a shared `TrendyolSyncController` exposes `POST stock-price/push` and `POST batch-requests/poll` alongside Phase 5's product endpoints. Added `Store.TgoStoreId` (migration `AddStoreTgoMapping`) so branches can map to Trendyol Go's store identifier once known. **Same endpoint-path caveat as Phase 5**: `getBatchRequestResult`'s path was never given in the brief either, so `TrendyolGoOptions.BatchResultEndpointPath` starts empty and polling reports "not configured" until set — the price-and-inventory push itself, unlike product creation, calls a real endpoint since its path was given verbatim. Refactored the shared 401/403/429/5xx message mapping (`TrendyolErrorMessages`) and batch-submit/parse logic (`TrendyolBatchSubmitHelper`) out of the product client so the new inventory client reuses it instead of duplicating it. Also fixed a bug caught while writing these tests: the inventory and batch-result clients would have thrown an unhandled `InvalidOperationException` (no `HttpClient.BaseAddress`) instead of failing gracefully when Trendyol Go isn't configured at all — added an explicit `IsConfigured` guard to both, matching the pattern the product client already had. Web gained "Stok/Fiyat Gönder" and "Parti Sonuçlarını Kontrol Et" buttons. 18 new tests (13 TrendyolGo unit + 5 integration) — 71 tests total, all passing (stable across repeated runs).
- [x] **Phase 7 — Sell/unsell**: `StoreProductInventory` gained `IsOnSale`/`UnsaleReasonCode`/`LastSyncedIsOnSale`/`SaleStatusLastSyncedAt` (migration `AddSaleStatusToInventory`). `PUT /api/stock-price/sale-status` lets you toggle a product's desired sale status per store locally (returns 404 if no stock/price row exists yet for that product+store). `ISaleStatusSyncService.PushChangedSaleStatusAsync` pushes only rows whose `IsOnSale` differs from the last-synced value, in batches, via `ITrendyolSellUnsellClient` — same delta-only pattern as Phase 6's stock/price sync, using `BatchOperationType.SellUnsell` for the `BatchRequestLog` rows. **Same endpoint-path caveat as Phases 5–6**: neither the sell/unsell endpoint path nor Trendyol Go's official unsell reason codes were given in the brief, so `TrendyolGoOptions.SellUnsellEndpointPath` starts empty (reports "not configured" until set) and the reason code is a free-text field rather than a guessed closed enum — the web UI takes it as plain text with a note to use Trendyol's real codes. Web gained per-row "Satışa Aç"/"Satıştan Kaldır" toggle buttons (with a reason input) in the stock/price editor and a "Satış Durumu Gönder" push button. 13 new tests (7 TrendyolGo unit — not-configured/endpoint-not-set/success/401/403/429/5xx — + 6 integration — toggle, 404 on missing row, delta-skip verified via direct DB assertion, batch log recording, auth checks) — 84 tests total, all passing (stable across repeated runs).
