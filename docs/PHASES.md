- [x] **Phase 9 — Order status workflow**: `ITrendyolPackageStatusClient` (`AslSu.TrendyolGo.PackageStatus`) adds `AcceptPackageAsync`/`InvoicePackageAsync`/`ShipPackageAsync`, each config-gated behind its own `TrendyolGoOptions.{Accept,Invoice,Ship}OrderEndpointPath` (`{packageId}`-templated) since none of the three were given in the integration brief — same "not configured" graceful-failure pattern as every other Trendyol client. `IOrderWorkflowService.{AcceptAsync,StartPreparingAsync,MarkPreparedAsync,DeliverAsync}` drives `Order.WorkflowStatus` through the local Yeni → Kabul Edildi → Hazırlanıyor → Hazırlandı → Teslim Edildi sequence one step at a time, validating the order's current step before allowing the next (an out-of-order or repeated call returns a 409). Accept/mark-prepared/deliver also best-effort notify Trendyol Go (accept/invoice/ship respectively) — critically, **the local step always advances regardless of whether that notification succeeds**, so the fulfilment workflow keeps working before those endpoints are configured; the notification outcome (`trendyolNotified`/`trendyolMessage`) is returned alongside the new status instead of blocking the transition. `Hazırlanıyor` (Preparing) is a pure local milestone with no Trendyol equivalent given in the brief. `OrdersController` adds `POST /api/orders/{id}/accept`, `/start-preparing`, `/mark-prepared`, `/deliver`. - [x] **Phase 11 — Webhook endpoint**: `WebhooksController` adds `POST /api/webhooks/trendyol-go` — `[AllowAnonymous]`, deliberately outside the JWT pipeline since Trendyol Go doesn't carry our tokens. `IWebhookService.ProcessAsync` handles a delivery in four steps: (1) validate the signature via `TrendyolWebhookSignatureValidator` (HMAC-SHA256 of the raw body, hex-encoded, constant-time compared) **only if** `TrendyolGo:WebhookSecret`/`WebhookSignatureHeaderName` are configured — neither the signature algorithm, header name, nor secret source was given in the integration brief, so an unconfigured webhook is accepted unverified (logged as a warning) rather than rejecting real deliveries against a guessed scheme; (2) best-effort parse an event type + dedupe key from common field names (`eventId`/`id`/`webhookId`/`packageId`/`orderNumber`), falling back to a SHA-256 hash of the raw body as the dedupe key when none is present — the payload schema is equally unconfirmed; (3) check `WebhookLog.ExternalEventId` (unique index since Phase 3) — a redelivery of an already-seen key returns `200` immediately without reprocessing; (4) record a `WebhookLog` row and best-effort trigger `IOrderSyncService.PullOrdersAsync` ("wired to order updates" — since the real payload shape isn't confirmed enough to update a specific order in place, a delivery instead refreshes all orders via the existing pull path), marking the log `Processed`/`Failed` accordingly. A bad signature (when configured) returns `401`; everything else returns `200` with `{accepted, signatureVerified, duplicate, message}`.

  11 new tests (5 TrendyolGo unit — signature match/case-insensitivity/wrong-secret/tampered-body/missing-signature + 6 integration — anonymous access, unverified-but-accepted when unconfigured, dedupe on resend, malformed-body fallback, signature rejected/accepted when configured) — 136 tests total, all passing (stable across repeated runs).
- [x] **Phase 12 — Polling fallback background service**: `OrderPollingBackgroundService` (`AslSu.Infrastructure.BackgroundServices`, registered via `AddHostedService`) runs continuously alongside the app as a fallback for order updates in case a Phase 11 webhook delivery is ever missed or Trendyol Go can't reach the endpoint yet — same `IOrderSyncService.PullOrdersAsync` path as the manual "Siparişleri Çek" button and the webhook handler, just on a timer instead of a click or a delivery. Polls every 45s (`NormalInterval`) while `TrendyolGoOptions.IsConfigured`; does nothing at all (no DB access, no network calls) when it isn't, so it's inert out of the box and in every test host. **Rate-limit aware**: if a poll's result message indicates Trendyol Go's rate limit was hit, the next poll is pushed out to `RateLimitBackoff` (3 minutes) instead of retrying at the normal cadence — on top of the existing per-request 429 retry-with-backoff already in the Trendyol Go HTTP client pipeline (Phase 4). Each cycle runs in its own DI scope (the service itself is a singleton; `IOrderSyncService` is scoped) and never lets one failed cycle stop the loop — exceptions are caught and logged, and the timer just continues at the normal cadence. A known, accepted limitation: this poller and a manual push racing to insert the *same brand-new* order at the same instant could hit the `PackageId` unique-index constraint — acceptable given how narrow that window is, and not worth locking machinery for.

  3 new unit tests (`OrderPollingBackgroundService.PollOnceAsync` — normal-success interval, rate-limit-message backoff interval, not-configured summary still completes without throwing) — 139 tests total, all passing (stable across repeated runs). No web changes this phase — purely a server-side background loop.
- [x] **Phase 13 — Background auto-sync service**: `ProductAutoSyncBackgroundService` automates what Phases 5–7 left as manual buttons on the Products page — every ~1 minute (`NormalInterval`) it runs, in order, `IProductSyncService.PushUnsyncedProductsAsync`, `IStockPriceSyncService.PushChangedInventoryAsync`, `ISaleStatusSyncService.PushChangedSaleStatusAsync`, then `IBatchPollingService.PollPendingBatchesAsync` — the same delta-only push logic and the same batch-result poll the manual buttons already used, just on a timer. A cycle where nothing actually changed is a handful of cheap DB queries and zero network calls, since each push step's own delta check (unchanged since Phases 5–7) short-circuits before ever touching Trendyol Go. Does nothing at all while Trendyol Go isn't configured, same as Phase 12's poller. **Rate-limit aware**: any step's result message indicating Trendyol Go's rate limit was hit backs the *whole* next cycle off to `RateLimitBackoff` (3 minutes) rather than just that one step. Each of the four steps is independently guarded — one step throwing doesn't stop the rest of the cycle from running, and the loop itself never stops on a bad cycle.

  3 new unit tests (`ProductAutoSyncBackgroundService.RunCycleAsync` — nothing-changed returns normal interval, any step reporting a rate limit returns backoff interval, one step throwing still lets the cycle complete) — 142 tests total, all passing (stable across repeated runs). No web changes this phase — purely a server-side background loop, nothing to configure beyond the credentials already required to configure Trendyol Go itself.
- [x] **Phase 14 — Logging/error-handling hardening**: a full audit of every `logger.Log*`/`Log.Error` call site under `backend/src` (Program.cs's global exception handler, both background services, `DbInitializer`, `WebhookService`) found no secret-leak risk anywhere — every logged message is either a static/sanitized string or a Turkish `Message` string that already went through `TrendyolErrorMessages`, never a raw response body, header, or credential. `TrendyolResponseHandler` captures the raw Trendyol response body on `TrendyolApiException.ResponseBody` for potential future server-side diagnostics, but a repo-wide check confirms it's never actually read or logged anywhere yet — it just sits on the exception object. `TrendyolGoAuthHandler` (Phase 4) already never logs the Authorization header it builds. `TrendyolSettingsService.GetSettings()` confirmed to only ever return `SupplierId`, a masked `ApiKey` (first/last 2 chars, rest `*`), and `IsConfigured` — `TrendyolSettingsDto` has no `ApiSecret` field at all, so there's no accidental-leak surface there by construction. Fixed one real (if previously low-severity) finding: Serilog's `ReadFrom.Configuration(...)` reads from a `"Serilog"` appsettings section by convention, but the app only ever had a vanilla ASP.NET Core `"Logging"` section — meaning that config block had **zero effect** on the actual logger and Serilog was silently running on its own bare default. Replaced it with explicit `MinimumLevel` calls directly in `Program.cs`'s `UseSerilog(...)`: `Information` baseline, `Warning` overrides for `Microsoft.AspNetCore` and `Microsoft.EntityFrameworkCore`, and — the security-relevant one — `Warning` for `System.Net.Http.HttpClient`, as defense-in-depth against `HttpClientFactory`'s built-in logging handler ever emitting request headers (including the Trendyol Go Basic Auth `Authorization` header) at Trace/Debug level, regardless of what any config file says now or later. Removed the now-confirmed-dead `"Logging"` blocks from `appsettings.json`/`appsettings.Development.json` rather than leaving misleading vestigial config in place; levels are code-only from here on for auditability, not appsettings-driven.

  No new tests this phase — no behavior changed, only startup-time logger configuration and the removal of inert config; the existing 142 tests continue to pass exactly as before, run 3x for stability.
